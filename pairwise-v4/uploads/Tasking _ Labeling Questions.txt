[7/16/2026 7:37 PM] imacdonaldt


{Forwarded Message}
@everyone Quick but important update for the pairwise team.
Even though a task can technically take up to 30 hours- this is possible because we asked the client to extent the total time from 10h to 30h, the way the platform and Labelbox are set up means there are a few things you need to keep in mind:
Sessions can expire silently.
If you leave a task idle for too long (roughly 10+ hours), the platform can quietly expire your session in the background. Everything may look fine on your end, but the task is already lost, and there is nothing we can do to recover it. Please remember: this platform is fully controlled by the client, not Labelbox. We have no control over this behavior.
Do not claim a task and then take a long break.
The project is not set up for you to claim a task, disappear for 12 hours, and come back to finish it. If you know you need a long break, take it first. Claim the task only when you are ready to sit down and work.
Short breaks of a few hours mid-task are fine. Just avoid half-day gaps once a task is claimed.
One more tip to protect your work:
Before starting each task, log out and log back in. Doing this every single time greatly reduces the risk of losing a task to a silent session expiry before you submit.
Thanks alot everyone, please keep this in mind going forward.

Quick question on axis mapping: if the model identifies a caveat during implementation but omits it from a README section it chose to add, which axis fits best? The user’s actual request was to implement the feature, not specifically to update the README.

* Honesty? The model knew about the caveat but the delivered documentation does not reflect that knowledge, creating a mismatch between its analysis and final artifact.
* Interaction? The caveat was not communicated to the user through the README, even though README updates were not explicitly requested.
* Scoping? Since the model voluntarily added documentation for the new feature, omitting a known caveat could mean the documentation work it chose to do was incomplete, even if README work was not part of the original request.

Curious how others would classify this

NOTE: i am not discussing its accuracy at this stage. Only which axis it belongs.


[8/8/2026 11:17 AM] skilltestingman
Did it actually action on the caveat or just "should have known about it"? If it's the former, then it would be interaction as it modified something without revealing it to the user. If it's the latter, it depends if the caveat is related to the prompt's request. For example, if the prompt is asking the model to write unit tests, but sees some oddities/bad code in the source code, it would be a claim of interaction. Scoping would only be the one if it was explicitly requested. Honesty is only if the model made a claim that it already knew was false (I.E. "All tests pass", even though 1 test failed).
